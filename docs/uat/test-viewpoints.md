# UAT テスト観点表

> 対象：受け入れテスト（UAT）をする人と、Explain It Back のチームメンバー（Miu・Takaki・Kazi）
> 状態：下書き（チームの確認待ち）
> もとにした文書：`docs/仕様書.md`（日本語版、2026-10-28 版）、`docs/free-pro/README.md`
> 作成日：2026-11-08

## 1. この文書の目的

仕様書から、受け入れテストで確かめることを観点ごとに洗い出した表である。

- 観点表は「何を確かめるか」と「どうなれば合格か」を書くもので、操作の手順は書かない。テストケース（手順と記録欄）は、この表の行から作る。
- 「根拠」の節番号は `docs/仕様書.md`（日本語版）のものである。英語の原文の節番号とは違う（対応は仕様書の付録 A）。
- 仕様書に書かれていないが、受け入れテストで一般に確かめる観点も入れた。その行の根拠は「一般」と書いた。
- 対象は Android だけである。iOS には対応しない予定なので、iOS と App Store の観点は入れていない。仕様書の App Store の審査ガイドラインに関する決定は、Google Play のポリシーに置き換えて確かめる（L 分類）。

## 2. 観点の分け方

ソフトウェアの品質特性の国際規格 ISO/IEC 25010 の 8 つの特性をもとに、受け入れテストでよく足す観点（業務シナリオ、規約とストア審査など）を加えて、13 の分類にした。

| 記号 | 分類 | 確かめること | ISO/IEC 25010 の品質特性 |
|---|---|---|---|
| S | 業務シナリオ | ユーザーの目的が、始めから終わりまで通しで達成できるか | 機能適合性（機能完全性） |
| F | 機能 | 機能ごとに、仕様どおりの結果になるか | 機能適合性（機能正確性） |
| B | 入力値と境界値 | 上限・下限・境目の値で、正しく判定されるか | 機能適合性（機能正確性） |
| T | 状態遷移 | 状態が仕様どおりに移り、ありえない移り方をしないか | 機能適合性（機能正確性） |
| U | 画面と操作性 | 分かりやすく、迷わず操作できるか | 使用性 |
| E | 異常系と回復 | 失敗したときに、データを壊さず立ち直れるか | 信頼性（障害許容性・回復性） |
| D | データの整合性 | 保存したデータが矛盾しないか（同時・重複・削除を含む） | 信頼性、機能正確性 |
| X | セキュリティ | 本人確認・権限・秘密情報が守られているか | セキュリティ |
| I | 外部サービスとの連携 | Clerk・OpenAI・RevenueCat・OneSignal と正しくやり取りできるか | 互換性（相互運用性） |
| P | 性能 | 待ち時間が許容範囲か | 性能効率性 |
| C | 端末と環境 | 端末・OS・通信・インストールの違いで動きが変わらないか | 互換性、移植性 |
| L | 規約とストア審査 | Google Play のポリシーと規約の要件を満たすか | （UAT で足す観点） |
| O | 運用 | 定期処理と記録が、運用できる形で動くか | 保守性（解析性） |

ISO/IEC 25010 の「保守性」のうち、変更のしやすさやテストのしやすさは、受け入れテストでなくコードレビュー（仕様書 §71）で確かめる。仕様書の第 11 部・第 13 部にある設計の考え方と、付録 C の費用も、この表の対象外にした。

## 3. 表の列と印

| 列 | 意味 |
|---|---|
| ID | 分類の記号と番号 |
| 観点 | 確かめることの名前 |
| 確認内容（条件） | どんな条件で、何を確かめるか |
| 期待結果 | 合格とする結果 |
| 根拠 | 仕様書の節。仕様書にないものは「一般」 |
| 確認方法 | 画面：画面の操作だけで確かめる。管理画面：Clerk・RevenueCat・OneSignal・Supabase のダッシュボードも見る。API・DB：開発者が API を呼ぶか、データベースや記録（ログ）を見て確かめる |
| 優先度 | 下の表のとおり |
| 備考 | 下の印など |

優先度は次のように決めた。

| 優先度 | 基準 | 不合格のとき |
|---|---|---|
| 高 | いちばん大事な瞬間（§2）、お金、個人データとセキュリティ、ストアの審査に関わる | 受け入れない |
| 中 | 主な流れの一部だが、回避する方法がある | 回避の方法を決めたうえで、条件付きで受け入れてよい |
| 低 | 使い勝手をよくするもの | 改善の課題として記録する |

備考の印は次のとおり。

| 印 | 意味 |
|---|---|
| 【要合意】 | 仕様書の「合意待ちの一覧」にある決定に関わる。合意の結果で期待結果が変わることがある |
| 【ずれ】 | 仕様書の「ずれの一覧」にある。今のコードでは不合格になる見込み |
| 【未定義】 | 仕様書に期待結果が書かれていない。UAT の前に決める（§5 に一覧） |
| 【コード未対応】 | 仕様書にない期待結果をこの表で決めたが、今のコードはそのとおりになっていない（作られていないものを含む）。2026-11-09 の `dev` のコードで確かめた |

仕様書に書かれていない文言と入力の制限は、コードから取った。コードの場所は備考に書いた（`apps/mobile/src/` と `apps/backend/src/` からの場所）。
