# Free / Pro のルール

> 対象：Explain It Back のチームメンバー（A / B / C）
> 方針（なぜサーバー側で判定するか）は `docs/spec.md` §32 Server-Side Entitlement Enforcement を参照。この資料は「何回まで使えるか、どう数えるか」をまとめたもの。
> 最終更新：2026-10-04（§1.1 復習上限の理由、§1.2 タイムゾーンを追記。§2 の提案をすべて決定事項に移動。§1.2 にプラン切り替えの検出方法を追記）

この資料では、項目を次の3つに分けています。

- **決定事項**：このルールで実装してよいもの
- **提案中（未確認）**：案は出ているが、まだ確定していないもの
- **未決定 / すり合わせが必要**：他の担当者との合意や、外部の情報が必要なもの

## 要点（3行）

1. 無料は **7日間で分析3回・復習18回**、Pro は **7日間で分析20回・復習120回**（Pro の上限は fair use limit）。
2. 上限は **ユーザーごとの7日間の固定ウィンドウ** で数える。分析と復習は同じウィンドウを使う。
3. 判定は **サーバー側のアップロード受付時** に行う（これが正式）。アプリ側のチェックは UX のためだけ。

## 1. 決定事項

### 1.1 プランごとの上限

| プラン | 分析 | 復習 | 位置づけ |
|---|---|---|---|
| 無料 | 7日間で3回 | 7日間で18回 | 無料枠の上限。上限に達したらペイウォールを表示する |
| Pro | 7日間で20回 | 7日間で120回 | fair use limit（乱用・コスト対策） |

復習の上限は **分析回数 × 6** で決めています。次の前提に基づきます。

```text
1回の分析 → 質問が3つ生成される
各質問を2回解く（最初の回答 ＋ 数日後の復習）
→ 3 × 2 = 6 回 / 分析
```

つまり、無料枠で行った3回の分析の復習は、すべて上限内でできます。復習を制限しても、復習で定着させるループ（spec §3.2 Loop B）は止まりません。

この前提（質問の数・復習の回数）が変わると、復習の上限も変わります（→ §3）。

### 1.2 ウィンドウの扱い

- **ユーザーごとの固定ウィンドウ**（fixed window）で数える。長さは無料も Pro も **7日間**。
- 分析と復習で **同じウィンドウを共有** する。
- **最初の利用**（分析 **または** 復習）を起点にウィンドウが始まる。7日経過した後の次の利用で、新しいウィンドウが始まる。
  - 「最初の分析」だけを起点にしない理由：ウィンドウの終盤に行った分析の復習が次のウィンドウにずれ込んだとき、復習だけでもウィンドウを開始できれば、例外処理が要らなくなる。
- **プランが切り替わったとき**（無料 → Pro、Pro → 無料のどちらも）は、それまでのウィンドウを終え、**切り替え後の最初の利用** から新しい7日間のウィンドウを始める。回数は 0 から数える。
  - 切り替えの検出方法：ウィンドウを始めたときのプランを保存しておき（`User.usageWindowPlan`）、利用時のプランと違っていれば切り替えがあったとみなす。Pro の期限切れによる Pro → 無料 は DB への書き込みなしで起きるため、書き込み時にリセットする方式では検出できない。

例：

```text
10/1 10:00  最初の利用      → ウィンドウ A 開始（10/8 10:00 まで）
10/3 18:00  利用            → ウィンドウ A で数える
10/8 10:00  ウィンドウ A 終了（この時点では何も起きない）
10/9 15:00  次の利用        → ウィンドウ B 開始（10/16 15:00 まで）。回数は 0 から
```

ウィンドウは「最後の利用から7日」ではなく「ウィンドウ開始から7日」で終わります。利用のたびに期限が延びることはありません。

ウィンドウは timestamp（開始時刻 ＋ 7日）で判定し、「日付の区切り」は使いません。そのため、タイムゾーン（time zone）によって結果が変わることはありません。

### 1.3 回数の数え方

- カウンター列を増減させる方式は **使わない**。判定のたびに、ウィンドウ開始以降のレコード数を数える。
- 復習の「1回」は、フォローアップ質問への **回答1回**（数え方を単純にするため）。
- 数えるのは **成功** と **実行中** のレコード。**失敗** した分析・評価は数えない。
- 実行中のまま一定時間（目安 **10分**）を過ぎたレコードは、止まったものとみなして数えない。
- 同時リクエスト対策として、トランザクションの中で次の順に処理する。

```text
BEGIN
  User の行をロック（SELECT ... FOR UPDATE）
  ウィンドウ開始以降の「成功 + 実行中」のレコードを数える
  上限未満なら「実行中」のレコードを作成する
COMMIT（ここでロックが外れる）
```

なぜロックが必要か：ロックなしで「数える → 作る」を行うと、同じユーザーの2つのリクエストが同時に「残り1回」と判定し、両方とも通ってしまいます（race condition）。User の行をロックすると、同じユーザーのリクエストは1つずつ順番に処理されます。

実装メモ：Prisma のクエリ API には `FOR UPDATE` がないため、interactive transaction（`prisma.$transaction(async (tx) => ...)`）の中で `$queryRaw` を使います。

### 1.4 チェックする場所

| 場所 | タイミング | 目的 |
|---|---|---|
| アプリ（mobile） | 録音開始時 | UX。録音してから断られるのを防ぐ |
| サーバー（backend） | アップロード受付時 | **正式な判定**。必ず行う |

アプリ側のチェックは改造したクライアントで回避できるため、判定の根拠にはしません（spec §32）。

### 1.5 上限到達時のエラーコード

| プラン | コード | HTTP status | アプリの表示 |
|---|---|---|---|
| 無料 | `FREE_LIMIT_REACHED` | 429 | ペイウォールを表示する |
| Pro | `USAGE_LIMIT_REACHED` | 429 | リセットまでの時間を表示する |

無料と Pro でアプリの表示が違うため、コードを分けます。以前の案の `DAILY_LIMIT_REACHED` は、7日間ウィンドウと名前が合わないため使いません。

HTTP status を 429 Too Many Requests にする理由：

- 429 は「一定時間内のリクエストが多すぎる」ことを表す（RFC 6585 §4）。無料・Pro どちらの上限も、7日間のウィンドウで区切った回数制限なので意味が合う。
- 403 Forbidden は主に権限の問題を表すため、時間が経てば解除される制限には合わない。402 Payment Required は「将来の利用のために予約」されているだけで、意味が標準化されていない（RFC 9110 §15.5.3）。
- アプリは status ではなく `error.code` で表示を分ける（`docs/error-handling/README.md`）。そのため、無料と Pro で同じ status を使ってよい。

注意：HTTP クライアントによっては 429 を自動で再試行します。上限は数日待たないと解除されないので、上限チェックがある API では自動リトライをしないでください（例：TanStack Query の query はデフォルトで3回リトライする。mutation はリトライしない）。

`apps/backend/src/lib/errors.ts` の `ERRORS` には、Phase 2 で上限チェックを実装するときに追加します（使い方は `docs/error-handling/README.md`）。

### 1.6 Pro の表記

「無制限」と書く場合は、fair use の上限があることを規約・説明文に明記します。上限があるのに「無制限」とだけ書くと誤解を招くためです。

### 1.7 モデルの使い分け

分析には高精度なモデル、復習の評価には安価なモデルを使います。回数の多い復習の費用を抑えるためです。具体的なモデル名は未決定です（→ §3）。

## 3. 未決定 / すり合わせが必要

| 項目 | 状況 | 影響 |
|---|---|---|
| 1回の分析で生成する質問の数、復習の間隔 | **B の担当**。B と合意が必要 | 変わると復習の上限（分析回数 × 6）も変わる |
| 録音の最大時間 | 未決定 | 費用見積もりでは **2分** と仮定 |
| Pro の価格 | 未決定 | 費用見積もりでは **月額980円** と仮定 |
| 使用する OpenAI のモデル名 | 未決定（分析は高精度、復習の評価は安価、という使い分けは決定済み → §1.7） | 確定前に、OpenAI 公式の料金ページで最新の金額を確認する |

## 4. 費用の目安（上限まで使った場合、1ユーザー・1か月）

| プラン | 費用の目安 |
|---|---|
| 無料 | 約 45〜210円 |
| Pro | 約 450〜1,410円（分析だけ高精度なモデルにした場合は約 790円） |

- 録音2分・Pro 月額980円の仮定に基づく（→ §3）。
- 平均的なユーザーは上限まで使わないため、実際の費用はこれより低くなる見込み。
- リリース後に利用状況を見て、上限を調整する前提。

## 5. spec §73 Product の質問への回答

| spec §73 の質問 | 回答 |
|---|---|
| How many free analyses? | 7日間で3回（§1.1） |
| Per day? week? month? | ユーザーごとの7日間の固定ウィンドウ（§1.2） |
