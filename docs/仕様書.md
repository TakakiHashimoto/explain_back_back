# 第 1 部　何を作るか

## 1. プロダクトの考え方

原文：§1

Explain It Back は、学んだばかりの概念をユーザーが自分の声で説明するスマホの学習アプリである。アプリは次のことをする。

1. 説明を文字に起こす
2. ユーザーがどれだけ理解しているかを分析する
3. 理解できている点を見つける
4. 説明に出てこなかった大事な点（抜け）を見つける
5. 間違って理解している点（誤解）を見つける
6. 説明に点数をつける
7. 追加の質問を作る
8. あとで答えた回答を評価する
9. 次に復習する日を決める
10. 弱いところを復習するよう、通知で知らせる

目指すのは、次のように感じられるアプリである。

> 「自分がどう説明するかを聞いてくれて、分かったつもりで実は誤解しているところを見つけてくれて、あとでもう一度思い出させてくれる先生」

次のように感じられるアプリは目指さない。

> 「文字を打ち込むと、ありきたりな AI の感想が返ってくる、よくあるチャット画面」

## 2. いちばん大事な瞬間

原文：§2

このアプリでいちばん大事なのは、本人が気づいていない微妙な誤解を見つける瞬間である。

例を示す。

```text
ユーザー：
「React の useEffect は分かっている」

ユーザーの説明：
「useEffect は描画の後に動いて、React は依存配列の中の変数を見張っている」

アプリ：
「エフェクトが描画の後に動く、という点は正しく理解できています。

ただ、説明からは『React が変数を見張っている』と考えているように見えます。

実際の React は、今回の描画での依存配列の値と、前回の描画での値を比べています。

確かめてみましょう。」
```

これがこのアプリの中心の価値である。ほかの機能はすべて、この瞬間を支え、長く覚えていられるようにするためにある。

## 5. 用語集

原文：§18、§51

チーム全員が同じ意味で使う言葉をまとめた。原文 §51 はこれらの言葉の意味を全員でそろえるよう求めている。

| 用語（モデル名） | 意味 | 決まったこと |
|---|---|---|
| User | アプリの中でのユーザー。Clerk のユーザーとは別に、アプリが自分で持つ | アプリの中の ID（UUID）を持ち、Clerk の ID は `authSubject` に入れる |

| Transcript | ユーザーが話した内容を文字に起こしたもの | |

| ReviewSchedule | 質問の次の復習日時 | |
| Entitlement | Pro を使える権利。RevenueCat からの通知で更新する | 【決定】このテーブルを正しい情報とする |

| 復習（review） | 質問・回答・予定をまとめた機能。モデル名の頭に `Review` を付ける。`Review` という単独のモデルは作らない | |

関係を図にすると次のようになる（原文 §18）。

```text

 │    │

 │          │
 │          ├── Transcript（文字起こし）
 │          ├── 点数

 │                        ├── ReviewAttempt（回答、何回でも）
```

## 9. 信用できる範囲の分け方

原文：§8

このプロジェクトのエンジニアリングで、いちばん大事な考え方である。外から来たデータは確認を通るまで信用しない。確認する場所を、原文は「境界」と呼んでいる。

```text
信用できない外からの入力
        ↓
境界（ここで確認する）
        ↓
```

## 16. アカウント削除

【決定】【要合意】

アプリの中でアカウントを削除できるようにする。App Store の審査ガイドライン 5.1.1(v) により、アカウントを作れるアプリは、アプリの中で削除もできなければならない。

削除するときは、そのユーザーのデータをすべて消す（`onDelete: Cascade`）。利用回数の記録も含めて、何も残さない。

### 16.1 削除の順番

先にデータベースのデータを消し、次に Clerk のユーザーを消す。データベースと Clerk は別のシステムなので、1 つのトランザクションではまとめて消せない。データベースを先に消しておけば、Clerk の削除に失敗しても、ユーザーのデータはもう消えている。Clerk の削除に失敗したときは記録（ログ）に残し、もう一度実行できるようにする。

### 16.2 登録し直したときの利用回数

削除してから同じメールで登録し直すと、利用回数が 0 に戻る。これは受け入れる。理由は次の 4 つである。

1. アカウント単位の制限は新しいメールアドレスでアカウントを作れば、そもそも回避できる。
2. 悪用しても最大 3 回分を前倒しで使えるくらいで、その代わりに学習の記録がすべて消える。
3. 防ぐ方法（メールアドレスを元に戻せない形で残す、端末ごとに制限する）は手間が大きく、締切に合わない。
4. 実際に悪用が見つかったら、後から足せる。

### 16.3 定期購入の解約の案内

削除の画面に、定期購入の解約方法の案内とリンクを入れる。支払いは Apple ID や Google アカウントに結びついているので、アプリのアカウントを消しても請求は止まらない。

## 18. 録音

原文：§10

録音はチームにとって初めての分野なので、仕組みから説明する。スマホのマイクは音の波を電気の信号に変え、それを数字の並び（デジタルのデータ）にする。

```text
人の声
    ↓
空気の圧力の変化
    ↓
マイク
    ↓
電気の信号
    ↓
アナログからデジタルへの変換
    ↓
数字の並び（サンプル）
    ↓
決まった形式の音声ファイルにする
```

React Native のアプリが受け取るのは、話した言葉でなく、手元の音声ファイルである。

```text
file:///.../recording.m4a
```

この時点でアプリが持っているのは `recordingUri`（音声ファイルの場所）で、`transcript`（文字起こし）はまだない。

【決定】【要合意】

- 録音は最大 2 分にする。この長さは変更の余地がある。2 分では足りないと感じたら延ばし、そのときは費用の見積もり（`docs/free-pro` §4）も見直す。
- ファイル形式は m4a（AAC）だけを受け付ける。Expo の録音機能（expo-audio）が標準で出す形式で、OpenAI の文字起こし API も受け付ける。

## 19. 音声のアップロード

原文：§11

ふつうの API のリクエストは JSON で送る。

```http
POST /topics
Content-Type: application/json
```

音声は文字でなくバイナリ（そのままのデータ）なので、最初の版では multipart/form-data（ファイルを送るための形式）を使う。

```http
POST /api/v1/topics/:topicId/explanations
Authorization: Bearer <トークン>
Content-Type: multipart/form-data
```

送る中身は次のとおり。

```text
audio=<音声ファイル>
duration=83（秒）
```

流れは次のとおり。

```text
スマホの中のファイル
        ↓
音声のデータを読む
        ↓
multipart のリクエスト
        ↓
HTTPS
        ↓
Express
```

`express.json()` は JSON しか読めないので、Express でファイルを受け取るにはファイルのアップロード用のミドルウェアが別に必要になる。

## 20. 音声の確認

原文：§12

アップロードされたファイルを、何でもすぐ OpenAI に送ってはいけない。サーバーはまず次のことを確認する。

```text
ファイルはあるか
ファイルの種類は許可したものか（m4a だけ）
ファイルの大きさは許容範囲か（例：10 MB まで）
録音の長さは許容範囲か（2 分まで）
ログインしているか
Topic は存在するか
Topic はこのユーザーのものか
このユーザーは、もう 1 回分析してよいか（利用回数）
```

確認する順番は次のとおり。

```text
リクエスト
   ↓
本人確認
   ↓
アプリの User に対応付ける
   ↓
Topic の持ち主の確認
   ↓
Pro の権利と利用回数の確認
   ↓
音声の確認
   ↓
文字起こし
```

OpenAI の文字起こし API には、1 ファイル 25 MB までという制限がある（公式ドキュメント。作る前に最新の値を確かめる）。2 分の m4a は数 MB なので、この制限に収まる。

## 21. 文字起こし

原文：§13

文字起こしは独立した 1 つの処理として扱う。

```text
音声
  ↓
OpenAI の文字起こしモデル
  ↓
文字起こし（Transcript）
```

たとえば音声で「useEffect lets you run side effects after rendering...」と話すと、同じ文が文字で返ってくる。音声認識の仕組みをバックエンドで作る必要はなく、音声を文字起こしのサービスに送って文字を受け取ればよい。

## 22. 文字起こしと分析の分離

原文：§14

次のように、AI が一度に最終的な答えまで出すとは考えない。

```text
音声 → AI → 最終的な答え
```

次のように 2 段階に分ける。

```text
音声
    ↓
文字起こし
    ↓
文字起こし（Transcript）
    ↓
分析
    ↓
理解度の評価
```

分けると、次のことができるようになる。

- 不具合の原因を探しやすくなる
- やり直しやすくなる
- 何が起きたかを追いやすくなる
- 文字起こしを確認できる
- 文字起こしをユーザーに見せられる
- 録音し直さずに、分析だけやり直せる
- 音声を聞き取る問題と、内容を考える問題を別々に扱える

## 23. 音声を保存しない方針

原文：§15

最初の版では次の流れにする。

```text
手元で録音
    ↓
アップロード
    ↓
文字起こし
    ↓
文字起こしを受け取る
    ↓
一時的な音声は捨てる
    ↓
文字起こしを保存する
```

本当に必要になるまで、音声をずっと保存することはしない。保存しなければ、次のものが要らなくなる。

- 音声の後片付け
- 長く保存する費用
- プライバシーの面倒な問題
- 音声をどれだけ残すかの決まり
- 失敗の原因が増えること

## 24. AI による分析

原文：§16

文字起こしができたら、文字起こしと Topic の情報を分析用の AI に送る。

```text
TOPIC
React の useEffect

ユーザーの説明
「……」

やること
次を分析する
- 理解できている点
- 抜けている概念
- 誤解
- 重要度
- 点数
- 追加の質問
```

AI には自由な文章で答えさせず、アプリが決めた形で返させる。形の例を示す。

```ts
type Analysis = {
  strengths: { concept: string; feedback: string }[];

  gaps: {
    concept: string;
    type: "MISSING" | "MISCONCEPTION";
    severity: "MINOR" | "MODERATE" | "MAJOR";
    feedback: string;
    question: string; // 弱点ごとの質問
  }[]; // 最大 3 つ

  scores: {
    accuracy: number;     // 正しさ
    clarity: number;      // 分かりやすさ
    completeness: number; // 網羅性
    overall: number;      // 総合
  };
};
```

【原文から変更】原文では `questions` が `gaps` と別の配列だった。この文書では弱点ごとに質問を 1 問持たせる形にした。フィールド名と enum の値も決定に合わせた。

### 24.1 質問を分析の中で作る理由

【決定】【要合意】

1 回の分析で、AI が弱点と、弱点ごとの質問をまとめて返す。理由は次の 4 つである。

1. 結果画面にすぐ質問を出せる。最初に通しで動かす目標（§66）とデモ（§79）は、分析結果と同時に質問が出る流れになっている。
2. 分析のときの AI はユーザーが実際に話した言い回しを見ているので、本人の誤解に合わせた質問を作れる。
3. 質問のない弱点ができない。§28 の「全部保存するか、何も保存しないか」に合う。
4. AI を呼ぶ回数と、利用回数の数え方が単純になる。

その代わり、分析の待ち時間は少し長くなる。処理中の表示（§30）で、待ち時間を感じにくくする。

### 24.2 弱点の数

【決定】【要合意】

弱点は最大 3 つにする。0 個（完璧な説明）も正常な結果として扱う。この数は変更の余地があり、変えるときは無料と Pro の復習の上限（§49）も見直す。

【未決定】点数 4 つの定義（何をもって 70 点とするか）と、`overall` を AI に出させるか、ほかの 3 つから計算するか（未-3）。

## 25. AI の出力の確認

原文：§17

決まった形で返させた AI の出力も、信用できない外のデータとして扱う。

```text
OpenAI の出力
     ↓
信用できない外のデータ
     ↓
実行時の確認
     ↓
アプリの中のデータ
     ↓
データベースと API
```

`type Analysis = ...` のような TypeScript の型を書いても、外の API が実行時におかしなデータを返すことは防げない。実行時の確認には Zod などのライブラリを使う。

【現状】Takaki の復習機能は Zod で形を確認したうえで、点数が 0〜100 の整数か、`correct` と点数が合っているかも確認している。分析でも同じように、弱点が 3 つ以下かなどを確認する。

## 27. セッションの状態

原文：§20

原文は処理の状態をどう持つかをチームで決めるよう求めていた。候補は `UPLOADING`、`TRANSCRIBING`、`ANALYZING`、`COMPLETED`、`FAILED` か、それより少ない状態である。状態が必要になるのは、文字起こしは成功して分析だけ失敗した場合に、録音し直さずに分析だけやり直したいからである。

【決定】【要合意】

最小限の状態にする。

```text
文字起こし完了（TRANSCRIBED） → 分析完了（COMPLETED）
                              → 分析失敗（FAILED） → やり直し → 分析完了
```

- 文字起こしが終わった時点で、セッションと文字起こしを保存する。
- 分析をやり直す API（例：`POST /api/v1/explanations/:sessionId/retry`）は、保存済みの文字起こしを使う。
- 失敗した分析は利用回数に数えない。やり直すときは、新しく 1 回分を確保する。

## 28. 分析結果の保存

原文：§36

分析が終わると、関係する複数の行を作る。

```text
弱点 A を作る
弱点 B を作る
質問 A を作る
質問 B を作る
点数と理解できている点をセッションに書き込み、状態を COMPLETED にする
```

トランザクションを使わないと、途中で失敗したときに中途半端なデータが残る。

```text
弱点 A    ✓
弱点 B    ✓
質問 A    ✓
質問 B    ✗ 失敗
```

分析結果は全部保存するか何も保存しないかのどちらかにする決まりなので、トランザクションを使う。

```text
開始（BEGIN）

弱点を作る
質問を作る
セッションを更新する

確定（COMMIT）
```

失敗したら取り消す（ROLLBACK）。

【原文から変更】原文ではセッションを作る処理もこのトランザクションに入っていた。この文書の決定では、セッションは文字起こしの時点で先に保存する（§27）。

## 31. 点数と理解できている点の保存

原文：§22

AI が返したものを、何でも新しいテーブルにする必要はない。理解できている点（`strengths`）が表示するだけのもので、独自の ID・寿命・関係を持たないなら、セッションに JSON として保存するだけで足りるかもしれない。

> 独自の ID、独自の寿命、単独で検索する必要、ほかとの関係、守るべき決まりのどれかがあるときに、テーブルを分ける。

【決定】2026-10-20

【決定】2026-10-20

理解できている点は、ExplanationSession に JSON の列を 1 つ置き、概念ごとの一覧をそのまま入れる。表示するだけで、中身で検索しないためである。

```ts
strengths: {
  concept: string;   // 理解できていた概念

}[];
```

【決定】2026-10-20 AI のコメントのフィールド名は `feedback` にする。原文の `explanation` は ExplanationSession の名前と重なるので使わない。弱点（`KnowledgeGap.feedback`）と回答の評価（`ReviewAttempt.feedback`）も同じ名前にそろえ、「AI がユーザーに向けて書いた文」は `feedback` と決めて読めるようにする。

## 35. 回答の評価と保存

原文：§25

原文の流れは次のとおり。

```text
質問
      ↓
ユーザーの回答
      ↓
Express
      ↓
権限の確認
      ↓
OpenAI で評価
      ↓
決まった形の評価
      ↓
実行時の確認
      ↓
回答を保存
```

評価の例を示す。

```json
{ "score": 91, "correct": true, "feedback": "正しく説明できています……" }
```

【決定】【要合意】

`POST /api/v1/review-questions/:questionId/attempts` は、次の順で処理する。

```text
① 本人確認
② 持ち主の確認（他人の質問なら 404）
③ 利用回数の上限の確認（reserveUsage）
     User の行をロック → 数える → 上限なら 429、まだなら「実行中」の記録を作る
④ AI による評価（トランザクションの外で行う）
     失敗したら記録を「失敗」にする（数えない）
⑤ トランザクション開始
     ReviewAttempt を作る
     ReviewSchedule を作る、すでにあれば更新する
     記録を「成功」にする（completeUsage）
   トランザクション確定
⑥ 評価結果と次の復習日時を返す
```

この順番にした理由は次の 3 つである。

- AI の評価をトランザクションの外に出すのは、AI の返事に数秒〜十数秒かかるからである。その間トランザクション（とロック）を持ったままだと、同じ行に触るほかのリクエストが待たされる。
- 記録を「成功」にする処理を ⑤ に入れると、回数に数えられたことと回答が保存されたことが必ず一致する。保存に失敗したら、回数も減らない。
- 上限の確認（③）を持ち主の確認（②）の後に置くと、存在しない質問や他人の質問へのリクエストで回数が減らない。

【現状】今のコードは評価して次の復習日を計算して返すだけで、回答も次の復習日時も保存していない。保存する関数 `saveReviewResult`（1 つのトランザクションで `ReviewAttempt` を作り、`ReviewSchedule` を作るか更新する）はできたが、まだ呼ばれていない。利用回数の確認もまだ入っていない（ずれの一覧）。

【現状】正解（`correct`）の条件は点数 85 以上と決まっている。AI にもそう指示し、受け取った後にも確認している。

## 36. 次の復習日の決め方

原文：§26

次の復習日は決まった計算をするアプリの処理で決める。AI には決めさせない。

```text
点数 50 未満 → 1 日後
50〜69       → 2 日後
70〜84       → 4 日後
85 以上      → 7 日後
```

AI に「このユーザーは次にいつ復習すべきか」と聞く必要はない。

```text
AI
→ 理解度を評価する

アプリ
→ 決まったルールで日程を決める
```

大会では、Anki のような本格的な間隔反復の仕組みは作らない。

【現状】この計算はアプリ側（`actions.scheduling.ts`）にもある。計算はバックエンドの仕事なので、アプリ側のものは使わない（ずれの一覧）。

## 37. 弱点の克服

原文は、弱点の「克服」が何を指すかを決めていなかった（原文 §73）。

【決定】【要合意】

2 回続けて正解（点数 85 以上）したら克服とみなし、それ以降は復習の予定を入れない。

```text
1 回目に正解 → 7 日後に復習の予定を入れる
7 日後にも正解 → 克服。KnowledgeGap.resolvedAt に克服した日時を入れ、通知も止める
途中で不正解 → 連続が途切れる。点数に応じた日程で、また予定を入れる
```

1 回の正解で終わりにすると、答えた直後だから覚えていただけでも終わってしまい、時間がたっても覚えているかを確かめられない。克服という区切りがないと通知がいつまでも増え続け、ユーザーが通知を切る原因になる。

【決定】2026-10-20

克服は `KnowledgeGap.resolvedAt`（克服した日時。克服していなければ空）で表す。新しいテーブルは要らない。

- 克服するのは弱点なので、弱点（`KnowledgeGap`）に置く。弱点と質問は 1 対 1 なので、質問からもたどれる。
- `ReviewSchedule.nextReviewAt` は空にせず、そのまま残す。期限が来た復習を探すときに「`resolvedAt` が空のもの」という条件を足せば、通知は止まる。克服を表す場所が 1 か所で済む。
- 克服した日時が残るので、「今週克服した弱点の数」のような進み具合も出せる。

回答を受け付けたときは、次の条件がすべてそろえば克服とする。練習かどうかを示す列は作らず、この比較で判定する。

```text
今回の回答が正解
かつ 今の時刻が nextReviewAt 以降（期限が来た後の回答）
かつ 直前の回答も正解
```

## 38. 期限の前の復習

【決定】【要合意】

質問には期限の前でもいつでも答えられる（練習として）。ただし克服の 2 回目として数えるのは、期限が来た後の回答だけにする。期限の前の回答も数えると、正解した直後にもう一度答えるだけで克服になってしまうからである。

【決定】2026-10-20

期限の前の練習で不正解だった場合も、克服の連続は途切れる。ふつうの回答と同じに扱い、点数に応じて予定を入れ直す。答えられなかったのなら、まだ定着していないので、早めに復習させる方がよい。どの回答も同じに扱うので、ルールも単純になる。

期限の前に正解した場合は、それが 1 回目の正解として扱われ、そこから 7 日後に予定が入る。そのため、§37 の条件だけで「期限前の正解は克服の 2 回目に数えない」も満たせる。

期限の前の回答も利用回数には数える。

## 40. 通知を送る時刻

【決定】【要合意】

通知は `nextReviewAt` の時刻のとおりに送る。15 分ごとに定期実行し、期限の来た復習を探して送る。

## 41. 通知の許可を求めるタイミング

【決定】【要合意】

最初の質問に答え終わったとき、まずアプリ独自の画面で「7 日後に復習をお知らせしますか？」と聞く。「はい」を選んだ人にだけ、OS の許可ダイアログを出す。

### 43.1 本番のサーバー

【決定】【要合意】2026-10-20

## 46. RevenueCat でのユーザーの指定

原文：§31

```text
Clerk のユーザー
      ↓
アプリの User.id
      ↓
RevenueCat のユーザー ID（App User ID）
```

OneSignal でも、できるだけ同じ `User.id` を使う。こうすると、メールアドレスに左右されない安定した方法でユーザーを指定できる。

【決定】2026-10-20（変更の余地あり。OneSignal の部分は【要合意】）

```text
Clerk でサインイン
   ↓
GET /api/v1/me で User.id を取る
   ↓
Purchases.configure({ appUserID: User.id })
OneSignal.login(User.id)
```

- このアプリはログインしないと使えないので、RevenueCat に匿名の ID を作らせない。RevenueCat は、ログインしてから購入するアプリでは、SDK を始める前に ID を決めて `configure` に渡すことを推奨している。`User.id` は推測できない UUID なので、RevenueCat が推奨する ID の条件にも合う。
- サインアウトしたときは `OneSignal.logout()` だけを呼ぶ。同じ端末で別の人がログインしたときに、前の人宛ての通知が届かないようにするためである。
- RevenueCat の `logOut()` は呼ばない。呼ぶと新しい匿名の ID ができてしまう（RevenueCat の推奨）。次にログインした人の ID で `logIn()` を呼ぶ。

- 購入
- 返金

RevenueCat はこれをバックエンドに知らせる（ウェブフック）。

```text
RevenueCat
    ↓
POST /api/v1/webhooks/revenuecat
    ↓
本当に RevenueCat からの通知か確認する
    ↓
どの User か特定する
    ↓
Pro の権利の状態を更新する
```

通知は必ず確認する。「このユーザーは Pro です」と言ってくる HTTP リクエストを、確認せずに信用してはいけない。

### 48.1 正しい情報の置き場所

【決定】

RevenueCat からの通知でバックエンドの `Entitlement` テーブルを更新し、このテーブルを正しい情報とする。購入した直後だけはアプリからバックエンドに最新の状態を取り込むよう依頼する。RevenueCat からの通知は購入から数秒遅れて届くことがあり、取り込みの依頼がないと、課金画面で購入した直後の分析が `FREE_LIMIT_REACHED` で断られてしまうからである。

`User.usageWindowPlan` は、その 7 日間の区切りを始めたときのプランを記録したものなので、`Entitlement` と同じ情報を 2 か所で持つことにはならない。

### 48.2 通知の確かめ方と処理

【決定】2026-10-20（変更の余地あり）

RevenueCat の公式ドキュメントによると、同じ通知はまれに 2 回以上届くことがあり、失敗すると最大 5 回まで送り直される。通知を受け取ったら `GET /subscribers` で最新の状態を取り直すことと、60 秒以内に 200 を返すことが推奨されている。

1. 本物かどうかは、RevenueCat のダッシュボードで設定した認証ヘッダー（Authorization）の値で確かめる。署名（HMAC）は受け取ったままの本文が必要で、今の `express.json()` の設定と合わないので、今は使わない。
2. 通知の中身は使わず、`GET /subscribers/{User.id}` で最新の状態を取り、`Entitlement` を上書きする。毎回最新の状態で上書きするので、同じ通知が 2 回届いても結果は変わらない。処理した通知の `id` を記録するテーブルは作らない。
3. 購入した直後の取り込み（§48.1）は `POST /api/v1/me/entitlement/sync` で行い、中身は 2 と同じ関数にする。
4. 処理が終わったらすぐ 200 を返す。

## 49. 無料と Pro の上限

`docs/free-pro` の内容で、原文 §73 の「無料で何回分析できるか」「1 日か 1 週間か 1 か月か」「Pro とは何か」「無料ユーザーは無制限に復習できるか」に答えたものである。

| プラン | 分析 | 復習 | 位置づけ |
|---|---|---|---|
| 無料 | 7 日間で 3 回 | 7 日間で 18 回 | 無料の上限。達したら課金画面を出す |
| Pro | 7 日間で 20 回 | 7 日間で 120 回 | 公正利用の上限（乱用と費用への対策） |

- 復習の上限は分析回数の 6 倍（質問 3 問を 2 回ずつ）にした。無料で分析した 3 回分の復習はすべて上限の中でできる。
- ユーザーごとの 7 日間の区切り（固定ウィンドウ）で数え、分析と復習は同じ区切りを使う。
- 最初の利用（分析か復習）から区切りが始まり、7 日たった後の次の利用で新しい区切りが始まる。
- プランが変わったら（無料から Pro、Pro から無料）、それまでの区切りを終え、変わった後の最初の利用から新しい 7 日間を始める。
- 日付の変わり目でなく開始時刻に 7 日を足した時刻で判定するので、ユーザーの地域の時刻に左右されない。

上限に達したときの返事は次のとおり。

| プラン | エラーコード | HTTP の状態 | アプリの表示 |
|---|---|---|---|
| 無料 | `FREE_LIMIT_REACHED` | 429 | 課金画面を出す |
| Pro | `USAGE_LIMIT_REACHED` | 429 | 次に使えるようになるまでの時間を出す |

- 429 を返すので、上限の確認がある API では自動のやり直し（リトライ）をしない。TanStack Query のデータ取得は、標準で 3 回やり直すので注意する。
- 「無制限」と書く場合は、公正利用の上限があることを規約と説明に書く。
- 分析には精度の高いモデルを、復習の評価には安いモデルを使う。具体的なモデル名は決まっていない（未-4）。

## 50. 利用回数の数え方

`docs/free-pro` §1.3

- 回数を足し引きする列は使わない。判定のたびに、区切りの開始以降の記録の数を数える。
- 回答 1 回を復習 1 回と数える。
- 数えるのは「成功」と「実行中」の記録で、「失敗」は数えない。
- 「実行中」のまま 10 分以上たった記録は、止まったものとみなして数えない。
- 同時に届いたリクエストへの対策として、トランザクションの中で次の順に処理する。

```text
開始
  User の行をロックする（SELECT ... FOR UPDATE）
  区切りの開始以降の「成功」と「実行中」の記録を数える
  上限未満なら「実行中」の記録を作る
確定（ここでロックが外れる）
```

ロックがないと、同じユーザーの 2 つのリクエストが同時に「残り 1 回」と判断して、両方とも通ってしまう（競合状態）。

質問を作る処理は分析の一部なので、復習としては数えない（§24）。回答のときの具体的な順番は §35 に書いた。

【現状】この処理（`reserveUsage`、`completeUsage`、`getUsage`）は `kazi` ブランチにあり、dev にはまだマージされていない。

## 51. Pro の価格

【決定】

月額 980 円と年額（例：7,800 円、約 2 か月分安い）を用意する。年額の金額はApp Store と Google Play で選べる価格の段階に合わせて決める。無料お試し期間は付けない。

# 第 9 部　失敗への備え

## 59. 失敗の種類と対応

原文：§46

失敗への対応もプロダクトの設計に含まれる。

### 59.1 マイクの許可を断られた

アプリで対応する。

```text
ユーザーが許可を断る
      ↓
なぜ必要かを説明する
      ↓
設定アプリへの移動か、やり直しを案内する
```

### 59.2 録音に失敗した

関係のない状態を失わずに、録音をやり直せるようにする。

### 59.3 アップロードに失敗した

オフライン、時間切れ、サーバーが応答しない、などの場合である。アプリはやり直せる状態を表示する。

### 59.4 本人確認に失敗した

ログインの期限切れ、正しくないトークン、トークンがない、などの場合である。バックエンドはリクエストを断り、アプリは Clerk のログインの回復の流れに沿って対応する。

### 59.5 権限の確認に失敗した

ユーザー A がユーザー B の Topic にアクセスしようとした、などの場合である。アプリで URL を手で作られても、バックエンドは断らなければならない（404 を返す。§13）。

### 59.6 文字起こしに失敗した

原文は対応の案として、次の流れを示している。具体的な状態の持ち方はチームで決めることとしていた。

```text
セッションがある
      ↓
文字起こしに失敗する
      ↓
失敗として記録する
      ↓
やり直せるようにする
```

【決定】§27 の決定では、セッションは文字起こしが終わった時点で保存する。文字起こしに失敗したときはセッションを作らず、利用回数も数えない。ユーザーは録音からやり直す。

### 59.7 文字起こしは成功し、分析に失敗した

特に大事な場合である。

```text
音声         ✓
文字起こし   ✓
分析         ✗
```

ユーザーに録音し直させなくて済むように、保存済みの文字起こしを使って分析だけやり直せるようにする（§27）。

### 59.8 AI の出力が正しくない

```text
OpenAI の返事
      ↓
実行時の確認に通らない
      ↓
正しくない結果は保存しない
      ↓
記録（ログ）に残す
      ↓
決まった形のエラーを返す
```

### 59.9 データベースへの書き込みに失敗した

保存に成功していないのに、分析結果を保存できたとユーザーに伝えてはいけない。

### 59.10 書き込みが途中で止まった

まとめて成功させるか、まとめて失敗させなければならない操作には、トランザクションを使う。

### 59.11 同じリクエストが重なった

大事な操作ごとに、次のことを考える。

```text
ユーザーがボタンを 2 回押したらどうなるか
通信が自動でやり直されたらどうなるか
時間切れの後にアプリが送り直したらどうなるか
```

使える手段は次のとおり。

```text
重複を許さない決まり
同じリクエストかを見分けるキー（冪等キー）
あれば更新、なければ作る操作（upsert）
トランザクション
重複したリクエストを取り除く処理
```

どこにでも使うのでなく、2 回実行されると実際に困る所だけに使う。

【決定】【要合意】2026-10-20

同じ録音が 2 回送られるのは不具合として扱い、アプリの側で起きないようにする。

- アップロードを始めたら、完了するか失敗するまで送信ボタンを押せなくする。
- 送信の処理（TanStack Query の mutation）は自動でやり直さない。mutation は標準では自動でやり直さないので、設定を変えないようにする。
- サーバー側の重複対策（冪等キーなど）は、今は入れない。

【決定】2026-10-20

アプリに結果が返らなかった分析（時間切れなど）は、利用回数に数えない。

次の 2 つを組み合わせて実現する。

1. サーバーの方が先に諦めるようにする。OpenAI の呼び出しに、アプリの待ち時間より短い制限時間を付ける（例：アプリは 120 秒待ち、サーバーは 90 秒で打ち切る）。サーバーが打ち切った分析は「失敗」になるので、利用回数に数えない（§50）。
2. それでもアプリが時間切れになったら、送り直さずに確かめに行く。「処理が終わっているか確認しています」と表示し、セッションの一覧（`GET /api/v1/topics/:topicId/explanations`）を取り直す。サーバーが保存し終えていれば、その結果を表示する。このとき利用回数は 1 回減るが、ユーザーは結果を受け取れている。

アプリが諦めても、サーバーは処理を続けていることがある。サーバーは、アプリが返事を受け取れたかどうかを知ることができないので、この 2 つで「結果を受け取れなかった分析は数えない」を満たす。サーバーに新しい仕組み（冪等キーなど）は足さない。

### 59.12 通知に失敗した

プッシュ通知に失敗しても、復習のデータがおかしくなってはいけない。復習の予定と通知を届けることは、関係はあるが別の問題として扱う。

## 付録 C　費用がかかる部分

仕様書の中で、費用に関係する箇所を集めた。金額は `docs/free-pro` §4 と §43.1 にある目安である。申し込む前と、OpenAI のモデル名を決めるとき（未-4）に、各社の料金ページで確かめる。

### C.1 使った分だけかかる費用（OpenAI）

OpenAI は文字起こし、分析、回答の評価の 3 か所で使う（§6.3）。

| パート | 節 | 費用に関係する決定 |
|---|---|---|
| 文字起こし | §21 | 録音は最大 2 分（§18）。延ばすときは費用の見積もりも見直す |
| 説明の分析 | §24、§49 | 精度の高いモデルを使う |
| 質問の生成 | §24.1、§33 | 分析と同じ呼び出しの中で作るので、質問を作るための呼び出しは別にない |
| 回答の評価 | §35、§49 | 安いモデルを使う。復習の上限は分析の 6 倍なので、上限まで使うと呼び出しの回数がいちばん多くなる |

OpenAI の費用を抑えるために、次のことを決めている。

- 利用回数に上限を設ける（§49、§50）。Pro の上限も乱用と費用への対策である。
- 上限の確認は OpenAI を呼ぶ前に行う（§20、§35）。上限に達したリクエストは OpenAI に届かない。
- 分析のやり直しには保存済みの文字起こしを使う（§27）。文字起こしの費用は 2 回かからない。
- 上限の確認がある API では、自動のやり直し（リトライ）をしない（§49）。
- 同じ録音が 2 回送られないよう、アプリの側で防ぐ（§59.11）。2 回送られると、利用回数も AI の費用も 2 回分になる。

上限まで使った場合の 1 ユーザー・1 か月の費用の目安は、次のとおりである（`docs/free-pro` §4）。録音は 2 分、Pro は月額 980 円と仮定している。

| プラン | 費用の目安 |
|---|---|
| 無料 | 約 45〜210 円 |
| Pro | 約 450〜1,410 円（分析だけ精度の高いモデルにした場合は約 790 円） |

### C.2 サーバーと外部サービスの費用

| サービス | 役割 | 費用 |
|---|---|---|
| Render（Web Service の Starter 1 台） | 本番のバックエンドと、15 分ごとの通知の処理 | 月 $7（1 ドル 150 円なら約 1,050 円）。ワークスペースの月額は申し込む前に確かめる（§43.1） |
| Supabase | PostgreSQL を置く場所 | 仕様書に金額の記載はない。無料プランに一時停止の制限があるかを、デモの前に確かめる（§43.1） |
| Clerk、RevenueCat、OneSignal | ログイン、購入と Pro の権利、プッシュ通知 | 仕様書に金額の記載はない |

音声は保存しないので、ストレージの費用はかからない（§23）。

### C.3 費用について確かめること

- 上限まで使う Pro ユーザーの費用の目安（最大で約 1,410 円）は、月額 980 円を超える。`docs/free-pro` §4 の見積もりには App Store と Google Play の手数料と、Render などのサーバーの費用は書かれていない。平均的なユーザーは上限まで使わない見込みだが、モデル名を決めるとき（未-4）に、Pro の上限と価格が釣り合うかを確かめる。
- 退会して登録し直すと、利用回数が 0 に戻る（§16.2）。そのぶん OpenAI の費用がかかるが、受け入れている。
- サーバーが 90 秒で打ち切った分析は、利用回数に数えない（§59.11）。それでも文字起こしの費用はかかる。打ち切った分析の呼び出しに費用がかかるかは、OpenAI の資料で確かめる。
- Apple Developer Program と Google Play の開発者登録の費用は、仕様書に書かれていない。
